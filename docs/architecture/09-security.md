# 09 — Безопасность: модель угроз и рекомендации

Механизмы описаны в [05 — Слой управления](05-governance-layer.md);
здесь — модель угроз и сквозные рекомендации.

## 1. Модель угроз (специфика AI-платформы)

| Угроза | Вектор | Контрмеры платформы |
|---|---|---|
| Prompt injection | Инструкции во внешних документах, результатах инструментов, сообщениях других агентов | Провенанс и trust levels на каждом фрагменте контекста; выходы моделей и внешние данные — недоверенные; политики «инструкции только из доверенных источников»; фильтры на входе контекста |
| Data poisoning | Отравленные документы в KB, ложные «воспоминания» | Trust levels, версионирование KB, источник у каждого чанка, карантин новых источников, аудит ingestion |
| Утечка данных через модель | PII/секреты в промптах к облачным провайдерам | Политики маршрутизации по классам данных (PII → только локальные модели), DLP-редакция, секреты никогда не попадают в контекст |
| Эскалация через инструменты | Агент вызывает инструмент за пределами намерения пользователя | Capability-модель, allow-list на агента, sandbox, подтверждение человеком для необратимых действий (obligation), лимиты автономии |
| Злонамеренный плагин | Сторонний код | Подпись пакетов, sandbox, permissions по манифесту, наблюдение за поведением (Threat Detection) |
| Runaway-агент | Циклы саморазмножения задач, исчерпание бюджета | Бюджеты действий/токенов/делегирований, глубина рекурсии, kill-switch (заморозка актора), admission control |
| Межарендная утечка | Общие индексы/кэши | Namespace-изоляция во всех хранилищах и кэшах, scope-фильтры памяти, тесты изоляции |
| Компрометация узла | Инфраструктура | mTLS между узлами, шифрование at-rest, минимальная доверенная база, секреты по lease |

## 2. Принципы

1. **Deny by default.** Любая способность (порт, инструмент, сеть,
   данные) выдаётся явно и минимально.
2. **Недоверие к контенту.** Выход модели, документ, результат
   инструмента, сообщение чужого агента — данные, а не команды.
3. **Полный аудит.** Каждое решение политики, вызов инструмента, доступ
   к памяти — в append-only журнале с криптографическим сцеплением записей.
4. **Человек в контуре по политике.** Классы действий (необратимые,
   финансовые, внешние публикации) требуют подтверждения — это
   obligation политики, а не опция кода.
5. **Секреты отдельно от знаний.** Хранилище секретов недоступно
   контексту моделей ни при каких условиях; выдача — короткоживущими
   lease инструментам в sandbox.

## 3. Рекомендации по этапам

- **Этап разработки:** контракты безопасности (permissions в манифестах)
  — с первого модуля; тесты изоляции scope-ов — в CI; фаззинг схем
  событий и API.
- **Перед продакшном:** threat modeling по каждому новому инструменту;
  pentest поверхности API; ревью политик по умолчанию (secure defaults).
- **Эксплуатация:** мониторинг аномалий поведения агентов; регулярная
  ротация секретов; учения по kill-switch; ревизия permissions плагинов
  при обновлениях.

## 4. Соответствие требованиям (compliance-ready)

Архитектура закладывает: право на забвение (управляемое удаление из всех
уровней памяти и индексов по субъекту), retention-политики, экспорт
аудита, локализацию данных (политики размещения по регионам — свойство
Storage-адаптеров), отчёты об использовании моделей (стоимость, объём,
классы данных).
