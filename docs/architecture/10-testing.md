# 10 — Рекомендации по тестированию

## 1. Пирамида тестирования AgentOS

| Уровень | Что проверяет | Особенности |
|---|---|---|
| Unit | Доменная логика внутри модуля | Чистый домен без инфраструктуры — тестируется без моков БД/сети |
| Contract | Порты и схемы событий | Consumer-driven contracts: каждый потребитель порта фиксирует ожидания; прогон против всех реализаций порта (встроенной и адаптеров) |
| Module | Runtime целиком с in-memory адаптерами | Модуль стартует в тестовом ядре с фейковыми портами |
| Integration | Взаимодействие модулей через шину | Сценарии на реальной шине + встроенных хранилищах; проверка идемпотентности (двойная доставка событий) |
| E2E | Сквозные сценарии через публичный API | Диалог с агентом, RAG-запрос, workflow с компенсацией |
| Chaos | Отказоустойчивость | Убийство модулей/узлов, задержки шины, отказ провайдера модели → проверка recovery и деградации |
| Load | Профили нагрузки | interactive p99, throughput индексации, burst мультиагентных сценариев |

## 2. Тестирование AI-специфики

Недетерминизм моделей требует отдельного подхода:

1. **Model Stub.** Тестовый адаптер `ModelPort` с записанными
   (record/replay) или скриптованными ответами — все тесты уровней
   Unit–E2E детерминированы и не тратят токены.
2. **Golden-датасеты + LLM-as-judge.** Качество (retrieval, ответы
   агентов, суммаризация памяти) оценивается офлайн на фиксированных
   датасетах; метрики качества — в CI как регрессионные пороги
   (допустимая дельта, не точное совпадение).
3. **Свойства вместо значений.** Для недетерминированных путей —
   property-based проверки: «ответ содержит провенанс», «контекст не
   превышает бюджет», «инструмент не вызван без разрешения политики».
4. **Симуляция агентов.** Sandbox-окружение, где агент проходит
   сценарии с подставными инструментами; проверяются границы автономии
   и соблюдение политик (adversarial-сценарии: prompt injection в
   документах, попытки эскалации).
5. **Replay-тесты.** Инцидент из продакшна (Event Log) воспроизводится в
   тесте — регрессия фиксируется навсегда.

## 3. Инфраструктура тестирования

- Каждый пакет контрактов поставляет **test-kit**: фейки портов,
  генераторы валидных/невалидных событий, golden-схемы.
- Матрица совместимости адаптеров: contract-тесты гоняются против всех
  поддерживаемых бэкендов (SQLite и PostgreSQL, in-memory и брокер).
- Тесты изоляции безопасности — обязательный набор: межарендная утечка,
  доступ вне scope, secret в логах/контексте (must fail).
- Версионирование схем проверяется автоматически: несовместимое
  изменение события/порта без bump major — ошибка CI.

## 4. Definition of Done модуля

Модуль считается готовым, когда: покрыт unit- и contract-тестами;
проходит module-тесты с двойной доставкой событий; манифест permissions
минимален и проверен; наблюдаемость видна в трассах; документация
контрактов сгенерирована; нагрузочный профиль снят.
